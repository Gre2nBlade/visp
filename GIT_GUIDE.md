# Git guide for Visp

## Ветки / Branches

- `feature/<short-name>` — новая функция / new feature
- `bugfix/<short-name>` — исправление / bug fix
- `test/<short-name>` — тесты / tests
- `docs/<short-name>` — документация / documentation
- `refactor/<short-name>` — рефакторинг / refactoring

## Коммиты / Commits

Первой строкой пишется тип и краткий результат на русском. После пустой строки —
английская версия. Первая строка нужна `release-please` для автоматического
определения версии; поэтому перенос сразу после `docs:` или `feat:` не используем.

- `feat` — новая функция / new feature
- `fix` — исправление / fix
- `docs` — документация / documentation
- `test` — тесты / tests
- `chore` — техническое изменение / maintenance
- `refactor` — рефакторинг / refactoring

Пример:

```text
docs: добавлена базовая документация Visp

EN: Visp foundation documentation added
```

Пишите о результате, а не о себе: «добавлен», «добавлена», «добавлено»,
«добавлены», «исправлена», «обновлены». Не используйте «добавил» и «исправил».
Английский вариант пишите в теле после `EN:`. Один коммит — один понятный
результат, без длинного отчёта.

## Версия

Используйте SemVer `MAJOR.MINOR.PATCH`.

- `PATCH` (`1.2.1` → `1.2.2`): до 3 файлов и небольшой объём без изменения API, UX-контракта или поведения интеграций.
- `MINOR` (`1.2.0` → `1.3.0`): новая совместимая функция, несколько связанных файлов, новый endpoint или плагинный capability.
- `MAJOR` (`1.0.0` → `2.0.0`): несовместимый API, формат кодов, миграция или изменение, требующее действий владельцев.

Правило «до 3 файлов» — ориентир, а не замена оценке влияния. Если маленькая правка меняет контракт, повышайте MINOR или MAJOR. Версию меняйте в одном месте источника истины (например, `pubspec.yaml`), а CI переносит её в сборку и changelog.

## Минимальный цикл

```text
git switch -c feature/code-limits
git add <files>
git commit -m "feat: добавлены лимиты кодов" -m "EN: Code limits added"
git push -u origin feature/code-limits
```

Начальная документация может быть опубликована в `main`. Дальнейшая разработка
идёт в отдельных ветках через pull request.

## Автоматическое управление версиями

В репозитории используется GitHub Action `release-please` (`.github/workflows/release.yml`). Он анализирует Conventional Commits после попадания изменений в `main`, создаёт release PR и предлагает следующую версию:

- `fix:` → PATCH;
- `feat:` → MINOR;
- `feat!:` или `BREAKING CHANGE:` → MAJOR;
- `docs:`, `test:`, `chore:`, `refactor:` сами по себе версию не повышают.

После слияния release PR Action создаёт Git tag, GitHub Release и обновляет changelog. Версия хранится в `.release-please-manifest.json`; при появлении Flutter-проекта Action также обновляет `pubspec.yaml` через `extra-files`. Если нужно пропустить релиз для технического коммита, используйте `chore:`.

Ручное изменение версии требуется только для особого релиза или миграции. Для обычной работы достаточно правильно выбрать тип коммита.
